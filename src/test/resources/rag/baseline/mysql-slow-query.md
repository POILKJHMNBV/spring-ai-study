# MySQL 慢查询排查指南

## 1. 数据库变慢是什么

数据库变慢通常不是 SQL 完全无法执行，而是请求延迟显著增加。

重点观察：

* SQL P95 / P99；
* 慢查询数量；
* 数据库连接池使用率；
* 获取连接等待时间；
* timeout rate。

平均耗时正常并不能排除问题，少量极慢请求可能导致 P99 明显恶化。

## 2. 数据库连接池异常

Java 服务通常使用 HikariCP 等数据库连接池。

常见指标包括：

```text
activeConnections
idleConnections
maximumPoolSize
pendingThreads
```

如果长期出现：

```text
activeConnections ≈ maximumPoolSize
pendingThreads > 0
```

说明新的业务线程已经开始等待数据库连接。

连接池接近满不一定意味着连接池配置太小，也可能是 SQL 执行时间增加导致连接长期无法释放。

## 3. 常见慢查询原因

常见原因包括：

* 缺少合适索引；
* 执行计划变化；
* 扫描或返回数据量过大；
* 锁等待；
* 长事务；
* 数据库 CPU、IO 或内存压力。

对于重点慢 SQL，应结合执行计划、扫描行数、返回行数和锁信息进一步验证。

不能仅根据“出现慢 SQL”就直接认定其为整个服务故障的根因。

## 4. 对 Java 服务的影响

数据库响应时间增加会延长业务线程持有数据库连接和等待 SQL 返回的时间。

可能表现为：

```text
DB P99 升高
→ 连接占用时间增加
→ activeConnections 增加
→ 请求处理时间增加
```

如果业务线程大量等待数据库，还可能进一步影响 Java 服务整体吞吐，但这一影响需要结合线程池指标单独确认。

## 5. 推荐排查顺序

首先检查：

```text
DB P95
DB P99
timeout rate
```

确认数据库延迟是否真的异常。

然后检查：

```text
activeConnections
maximumPoolSize
pendingThreads
```

判断连接池是否开始形成瓶颈。

接着定位执行时间最长或调用次数最多的 SQL，并检查执行计划、索引、锁和事务情况。

最后确认数据库异常时间是否与当前业务故障时间一致。

## 6. 判断原则

如果观察到：

```text
DB P99 明显升高
activeConnections 接近 maximumPoolSize
pendingThreads 增长
```

可以判断数据库响应变慢已经开始影响连接池和上游请求。

但不能仅凭这些指标确认一定是缺少索引、锁等待或某一条 SQL 导致。

这些根因需要继续通过 SQL 和数据库指标验证。

## 7. 处理原则

不要优先通过扩大连接池解决数据库变慢。

正确顺序是：

```text
确认数据库延迟
→ 检查连接池
→ 定位慢 SQL
→ 检查执行计划 / 锁 / 事务
→ 优化真正瓶颈
```

如果数据库本身已经达到处理瓶颈，增加连接数反而可能增加数据库压力。
